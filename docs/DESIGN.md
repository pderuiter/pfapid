# pfapid: design

pfapid is a REST API for OpenBSD pf, built to be driven by Terraform
([terraform-provider-pf](https://github.com/pderuiter/terraform-provider-pf)).
This document explains how it drives pf, why it is shaped the way it is, and
which pf behaviour (verified on OpenBSD 7.9) the design relies on.

## 1. Summary

One Go daemon runs on the firewall. It does **not** talk to `/dev/pf` through
ioctls. It renders validated, typed objects into pf.conf syntax and loads them
with `pfctl`, scoped to **anchors** the API owns. The daemon is
privilege-separated in the OpenBSD style: the network-facing process is
unprivileged and locked down with `pledge`/`unveil`, and a root process accepts
only structured requests and runs nothing but `pfctl`. Every change goes
through **validate → apply → commit-confirm with automatic rollback**.

## 2. How to drive pf

| Option | Verdict |
|---|---|
| **A. Render pf.conf syntax and load it with `pfctl` (per anchor)** | **Chosen.** pf.conf is the stable, documented interface. `pfctl -nf` gives free validation, and loading an anchor is atomic. Cross-compiles with `CGO_ENABLED=0`. |
| B. ioctls on `/dev/pf` | Rejected. The `pfvar.h` struct layouts change between OpenBSD releases with no ABI promise, so every upgrade would put the firewall at risk. |
| C. Wrap configuration management (Ansible etc.) behind an API | Rejected. Slow, no fine-grained read-back, no drift detection. |

### Anchors as the ownership boundary

The base `/etc/pf.conf` stays with whoever manages the firewall today. It
holds the defaults, `antispoof`, the management and API pass rules (lockout
protection) and the hooks pfapid needs:

```pf
set block-policy drop
block all
pass in quick on mgmt proto tcp from $admin_nets to self port 8443   # pfapid; the API cannot touch this
...
anchor "api/*"                          # everything below is owned by pfapid
include "/etc/pf.anchors/api.conf"      # generated by pfapid: one `load anchor` line per anchor
```

* Each Terraform-managed unit, for example one Kubernetes cluster's access
  policy, is a **named anchor** `api/<name>`. Its file is written to
  `/etc/pf.anchors/api/` so it survives a reboot, and it is loaded live with
  `pfctl -a api/<name> -f -`.
* Authorisation maps onto anchors: a client can be scoped to `k8s-prod*` and
  cannot touch anything else.
* pfapid never edits the base file. The generated include keeps new anchors
  persistent without a change to the base ruleset.

## 3. Objects and how they map to pf

| API object | pf construct | Notes |
|---|---|---|
| Anchor (filter + NAT rules) | `pass`/`block`/`match` with `nat-to`, `rdr-to`, `binat-to`, `af-to` | An ordered list of rules is one resource and one atomic load, because pf is order-sensitive. |
| Table | `table <name> persist` + `pfctl -t name -T replace` | Tables are declared empty in the base ruleset; pfapid owns their contents. Changing entries does not reload rules. |
| Referenced table | a base-ruleset table, often `const` | `policy.ref_tables`: rules may name it (`<rfc1918>`), but pfapid never reads or changes its contents and it cannot be PUT. A name is either managed or referenced, never both. |
| QoS | HFSC `queue` trees (`bandwidth`, `min`, `max`, `qlimit`, `default`, `flows`/`quantum` for FQ-CoDel) plus `match` rules with `set queue` / `set prio` | Lives in the main ruleset (§8). ALTQ was removed in OpenBSD 5.5 and is not modelled. |

### Rule addresses and ICMP types

An endpoint is `any`, one or more prefixes, a table, an interface's own
addresses `(name)` or `self`, optionally with ports. `negate` puts `!` in
front of the address (`to ! <rfc1918>`). It is allowed only on a single
address: pfctl expands `{ !a !b }` into one rule per element, and two pass
rules `to !a` and `to !b` together match everything, including a and b.
"Everything except several prefixes" is a negated table. A negated prefix is
never treated as internal by the NAT check.

`icmp_types` adds `icmp-type` (protocol `icmp`) or `icmp6-type` (protocol
`icmp6`): pf's type names for that protocol, or numbers 0..255. ICMP codes
are not modelled.

### Interface groups

pf rules refer to **interface groups**, never to device names, so they keep
working when a device is renumbered or replaced and when VLANs are added. The
reference layout has three groups: `mgmt` (read-only for the API; carries the
pfapid listener), `frontend` and `backend` (VLANs join the group with
`ifconfig vlanN group frontend`). The policy in the configuration lists the
groups the API may use; `mgmt` can never be one of them.

### IPv4 and IPv6

Every object is dual-stack. Address fields are `netip.Prefix`/`netip.Addr`,
and rules carry an explicit `family` (`inet` or `inet6`). The renderer always
writes the family. A rule that mixes families is **rejected**: pfctl would
silently expand it into one rule per family, and then what is loaded no longer
matches what was rendered. A rule that must cover both families references a
table, which may hold both.

NAT flavours: `nat-to` (v4 and v6), `rdr-to`, `binat-to` (same-length v6
prefixes give NPTv6-style mapping) and `af-to` (NAT64 / NAT46). Translation
happens on `match`, filtering on `pass`, and the API renders both, so a NAT
cannot silently drop traffic. By default pfapid refuses NAT between two
networks listed in `policy.internal_nets`; `allow_internal_nat` turns that off.

The base ruleset must keep ICMPv6 neighbour discovery (types 133–137),
packet-too-big, time-exceeded and parameter-problem open; the API cannot block
them.

## 4. Security design

### 4.1 Privilege separation

```
 Terraform / CI ──mTLS──▶ pfapid child (user _pfapid)
                            unveil("/", "") + pledge("stdio inet"): opens no files
                            • TLS, authN/authZ, rate limits, strict JSON decoding
                            • builds typed objects only
                                  │  length-prefixed JSON over a socketpair
                                  ▼
                         pfapid parent (root)
                            pledge("stdio rpath wpath cpath fattr proc exec")
                            unveil: pfctl (x), anchor dir, include file dir,
                                    state dir, TLS files (r), /dev/null
                            • validates every object again (the child is not trusted)
                            • renders config from typed values
                            • execve with a fixed argv, never a shell string
```

The parent reads `/etc/pfapid.json` and the TLS files, reconciles, then
re-executes itself as `_pfapid` with a socketpair on fd 3. The child receives
its listen address, TLS material and client list in one bootstrap message,
opens its listening socket, and then locks itself down. IPC messages are
capped at 4 MiB, one request at a time.

### 4.2 Injection is threat number one

pfapid writes files that pf parses, so a newline or `}` that slipped into a
field would become a rule.

* No free-form strings reach the renderer. Addresses are `netip` types, ports
  are numeric ranges, actions and protocols are enums, interfaces come from an
  allow-list.
* Names (anchors, tables, queues, labels) must match `^[a-z][a-z0-9_-]{0,30}$`.
* After rendering, a guard checks one line per rule and rejects `include`,
  `anchor`, `load`, `table`, `queue` and macros. pfctl accepts `include` and
  inline `anchor { }` inside anchor files (§7, T7), so this check matters.
* `pfctl -nv` validates the result before anything is loaded.
* The renderer is fuzzed (`FuzzAnchor`) with the property that any input is
  either rejected or renders to exactly one guarded line per rule.

### 4.3 Transport, authentication, authorisation

* TLS 1.3 only, client certificate required. Certificates: §9.
* A client is identified by certificate CN or SPIFFE ID, always bound to the
  CA bundle it was issued from.
* Scopes per client: anchors (exact or `prefix*`), tables, `qos`, `read_only`,
  `admin`. A `read_only` client may GET, and may also call the two validate
  endpoints (`POST /v1/anchors/{name}/validate`, `POST /v1/qos/validate`):
  they only render and run `pfctl -n`. That lets a plan-only identity, such
  as merge-request pipelines, run `terraform plan` without being able to
  change anything. Anchor scope and the `qos` grant still apply.
* Listen on the management address only, and let the base ruleset allow the
  port from the admin networks only.
* 1 MiB request limit, unknown JSON fields rejected, a token bucket per client,
  server timeouts.

### 4.4 Change safety

* **Commit-confirm.** A change is loaded, then pending until the same client
  (or an admin) calls `POST /v1/changes/{id}/confirm`. Not confirmed within
  `confirm_timeout` (10s–10m, default 60s): reverted by the root process. Only
  one change may be pending (409 otherwise). The Terraform provider confirms
  after a successful apply and rolls back explicitly when confirming fails.
* The state directory holds only committed state. A restart while a change is
  pending reverts it.
* Concurrency: every object has an ETag; updates and deletes require
  `If-Match`, creates `If-None-Match: *`.
* The base ruleset keeps management and API access, so lockout through the
  API is structurally impossible.
* Every mutation and failure is logged with the client's identity.

### 4.5 Drift detection

GET returns live state. pfctl normalises rules (`port = 80`, `flags S/SA`,
dropped `keep state`) and expands `{ }` lists, so drift compares the output of
`pfctl -nv` on the rendered text with `pfctl -a <anchor> -sr`, never source
with live. The renderer uses no macros and expands lists itself, so object and
rule stay 1:1. Tables compare with `pfctl -t X -T show`.

## 5. API

REST + JSON under `/v1`, described in `api/openapi.yaml` (OpenAPI 3.1). A unit
test fails when a route is added without being described.

`GET /v1/healthz`; `GET /v1/anchors`, `GET|PUT|DELETE /v1/anchors/{name}`,
`POST /v1/anchors/{name}/validate`, `GET /v1/anchors/{name}/drift`;
`GET /v1/tables`, `GET|PUT /v1/tables/{name}`, `GET /v1/tables/{name}/drift`;
`GET|PUT /v1/qos` (an empty document removes QoS), `POST /v1/qos/validate`, `GET /v1/qos/drift`;
`GET /v1/changes/pending`, `POST /v1/changes/{id}/confirm|rollback`.

`/validate` runs pfctl on the rendered text, so the provider fails
`terraform plan` on anything pf would refuse.

## 6. Change flow (anchors)

1. Validate the model → render → guard → `pfctl -nv -a api/<n> -f`.
2. `pfctl -a api/<n> -f`, move the file into place, regenerate `api.conf`.
3. Pending until confirm; on confirm the state directory is updated and the
   history records `confirmed`, otherwise `rolled_back` or `expired`.

## 7. pf behaviour this design relies on (OpenBSD 7.9)

| # | Question | Result | Consequence |
|---|---|---|---|
| T1 | Queues in anchors? | **No:** "must not have queue definitions in an anchor". | Queue definitions live in the main ruleset. |
| T1b | Can an anchor rule `set queue` a main-ruleset queue? | **Only when the anchor is loaded as part of a main load.** A runtime `pfctl -a X -f` fails with "queue … is not defined". | QoS is its own domain, applied by a main reload (§8). Normal anchors may use `set prio` but not `set queue`. |
| T1c | Queue on an interface group? | **No:** "not an interface". | Root queues name a physical interface from `policy.queue_interfaces`. |
| T1d | `flows` (FQ-CoDel) | Works. | Modelled with `quantum`. |
| T1e | Bandwidth in percent? | **No:** "no bandwidth in % yet". | Bit rates only (`100M`). |
| T1f | Children adding up to more than the parent? | Accepted by pfctl. | pfapid refuses it. |
| T1g | Root without a default queue? | Refused. | Validated up front: exactly one default leaf per tree. |
| T1j | `match out … set queue` on a connection opened from outside | Never matches: the state was created inbound. | Classify on the state-creating rule (`match in`). |
| T2 | Table scope | An anchor rule naming a table it doesn't define uses the global table. An anchor table with the same name shadows a global one with only a warning. | Table names must be unique; shared tables are global. |
| T3 | `pfctl -nvf` vs `pfctl -a X -sr` | Identical rule lines (apart from macro definitions). | Basis of drift detection (§4.5). |
| T4 | Atomic anchor load | A broken load leaves the old anchor unchanged. | Relied on; still validated first. |
| T5 | Does reloading the main ruleset wipe runtime anchors? | No. | Base reloads (and QoS applies) are safe. |
| T6 | Table entries vs reload | A table declared **with** contents is reset on reload; declared empty with `persist`, runtime entries survive. | Base tables the API fills are declared empty. |
| T7 | Hostile input | A stray `}` is rejected, but `include` and inline `anchor { }` inside an anchor file are **accepted**. | The post-render guard (§4.2). |
| T8 | Speed | 20 loads of a 200-rule anchor ≈ 1 s; replacing 5,000 table entries < 1 s. | Applies are synchronous. |
| T9 | Interface groups | VLANs with `group frontend` match `on frontend` rules. | Rules use groups. |
| T10a | Mixed-family rule | Silently expanded into one rule per family. | Rejected by the model. |
| T10c | `binat-to` with different v6 prefix lengths | Accepted by pfctl. | pfapid validates equal lengths. |
| T10e | No-family rule referencing a mixed v4/v6 table | Stays one rule. | Tables cover both families. |

Traffic tests confirmed the filter and QoS paths end to end: a `block return`
from a client's /32 and /128 (directly and through a table), and a 2 MB
download shaped to 2 Mbit/s in a 2M queue over both IPv4 and IPv6, while the
default queue was unshaped.

## 8. QoS

QoS is one document per firewall (`/v1/qos`, `pf_qos`): HFSC queue trees plus
classification rules.

* **Base ruleset hooks:** `include` of the queue file, plus the `api-qos`
  anchor loaded from the rules file, both before `anchor "api/*"`.
* **Apply:** both files are written and the base ruleset is reloaded. The
  reload is atomic and anchors and tables survive it (T5/T6). If it fails, the
  old files are restored.
* **Validation:** `pfctl -nv` on a minimal main ruleset containing only the
  QoS files gives the normalised form used for drift; `pfctl -n` on a copy of
  the real base, with the hooks pointed at the candidate files, proves the
  whole ruleset still loads.
* **Rules classify only:** `match` rules, no `pass`/`block`/NAT, so QoS can
  never change what the firewall permits. A separate `qos` client grant.
* Not yet: HFSC burst (`bandwidth X burst Y for Nms`).

## 9. Certificates, identity and key protection

pfapid does not push anyone towards one PKI. See
[CERTIFICATES.md](CERTIFICATES.md) for the operator guide.

* **Files are the interface.** pfapid reads `tls.cert`, `tls.key` and named CA
  bundles (`tls.client_cas`) and re-reads them every `tls.reload_interval`
  (default 1m). The child asks the parent over IPC and swaps its `tls.Config`
  atomically, so it still opens no files. Bad material is logged and the old
  material kept; material that drops a bundle a client needs is refused.
* **Default: built-in self-signed PKI** (`pfapid pki init|issue|renew`):
  ECDSA P-256; a CA with pathlen 0 valid 10 years; server certificates valid
  397 days and client certificates 90 days; files created with `O_EXCL`, keys
  0600; `renew` replaces the server pair atomically, key first.
* **Bring your own CA:** add the company CA as another bundle (preferred: no CA
  key on the firewall), or let pfapid sign with a dedicated intermediate
  (`-ca-cert/-ca-key`; the key is never copied). Encrypted PEM keys are refused.
* **Identity: CN or SPIFFE ID.** A client with `spiffe_id` matches only an
  X509-SVID-style certificate whose single URI SAN equals it; otherwise the CN
  must equal its name. Matching is scoped to the client's CA bundle, found from
  the trust anchor of the verified chain, so a second CA cannot mint a
  certificate that impersonates a client of the first. One CA certificate in
  two bundles is rejected. SPIRE works through spiffe-helper writing files;
  there is no SPIRE agent for OpenBSD.
* **No TPM.** OpenBSD 7.9 has no TPM userland (tpm(4) only handles suspend,
  there is no device node and no TSS tooling), so a hypervisor-provided vTPM
  cannot seal pfapid's keys. Mitigations instead: key files root-only and read
  only by the root process; the network process holds the server key only in
  memory under `pledge("stdio inet")`; short certificate lifetimes with reload;
  CA keys off the firewall; encrypted VM storage if disk theft is in scope.
  Revisit if OpenBSD gains a TPM 2.0 userland.

## 10. Roadmap

* Metrics endpoint (apply count, rollbacks, drift, `pfctl -si` counters).
* Phase 2, riskier because a wrong change can cut off the management path, so
  the management interface stays read-only and everything uses commit-confirm:
  * VLANs and other interfaces (`hostname.if` + `sh /etc/netstart`);
  * CARP and pfsync (CARP passwords never returned on GET; pfsync on an
    isolated link);
  * IPsec with iked (IKEv2 only; `iked -n` validates, `ikectl reload` applies);
  * IPv6 router advertisements (rad) and prefix delegation (dhcp6leased).
* HA: pfsync replicates states, not rules. Configure each node through
  Terraform provider aliases.
